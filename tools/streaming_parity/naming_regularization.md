# MobilityNebula SQL-token naming: the regular rule

## The rule (one line)

> A Nebula SQL function token is **exactly the genuine backing MEOS C symbol, uppercased**.
> `token == meos_call.upper()`, and the operator class is its CamelCase
> (`econtains_tgeo_geo` → token `ECONTAINS_TGEO_GEO` → `EContainsTgeoGeo{Logical,Physical}Function`).

This is the same convention the from-MEOS-API binding codegen targets ecosystem-wide:
given a MEOS/MobilityDB symbol, the binding name is derived mechanically — no
per-function hand-naming. It makes a new MEOS function/type a *generated* rollout
(the `minDistance` function-rollout and `tbigint` type-deployment templates were
the first hand-applications of this same idea; this codifies it).

## Why this matters for auto-rollout

When a new symbol `foo_bar_baz` lands in MEOS:

1. token `FOO_BAR_BAZ`, classes `FooBarBaz{Logical,Physical}Function` — all derived.
2. `codegen_nebula.py` emits the operator + grammar token + parser glue from the
   signature in `meos-idl.json` (MEOS-API), no naming decisions.
3. The streaming-parity adapter credits it because `token.lower()` is an exported
   symbol (`nm -D`) — the L1/L2/L3 gates stay mechanical.

No step requires a human to choose a name. That is the whole point: regular naming
*now* is what lets the catalog drive the binding later.

## Migration outcomes for the legacy (irregular) tokens

`naming_regularization_map.tsv` holds the full `legacy_token → genuine_meos_symbol →
regular_token → outcome` table. Three outcomes:

- **RENAME (92)** — a genuine distinct MEOS symbol exists and no regular token owns
  it yet; the token is just spelled irregularly. `TEMPORAL_NAD_TGEOMETRY →
  NAD_TGEO_TGEO`, `TGEO_CENTROID_EXP → TGEO_CENTROID`, `BIGINT_EXTENT →
  BIGINT_EXTENT_TRANSFN`, mixed-case `NAD_TFloat_Float → NAD_TFLOAT_FLOAT`.

- **COLLAPSE (75)** — the operator composes via a symbol owned by *another* regular
  token, because MEOS exports **no** type-specific symbol. These are redundant
  duplicates and fold into the genuine token (minimize-the-API):
  - tnpoint/tpose spatial-rels (`econtains/eintersects/etouches/edisjoint/adwithin/...`)
    all call `*_tgeo_{geo,tgeo}` (MEOS has no `econtains_tnpoint_geo`,
    `econtains_tpose_tpose`, ...) → fold into `ECONTAINS_TGEO_GEO` / `..._TGEO_TGEO`.
  - `TEMPORAL_TFLOAT_AVG_VALUE` + `TEMPORAL_TINT_AVG_VALUE` → `TNUMBER_AVG_VALUE`
    (avg lives at the `tnumber` superclass; `tfloat_avg_value` is not exported).
  - the `TEMPORAL_NAD_T{POSE,NPOINT}_{TPOSE,TNPOINT}` / `..._GEOMETRY` composition
    wrappers, whose regular `NAD_T{POSE,NPOINT}_*` token is already owned by the
    direct operator → the wrapper is removed.
  - Note: tcbuffer rels and `nad_t{npoint,pose,cbuffer}_*` (the *direct* operators)
    ARE genuine exported symbols → those RENAME, they do not collapse.

- **BENCHMARK_KEEP (2)** — `PAIR_MEETING`, `TEMPORAL_SEQUENCE`: BerlinMOD-benchmark
  helpers with no single 1:1 MEOS symbol; left as-is, documented.

Regular tokens already in the grammar (e.g. `ADD_TNUMBER_TNUMBER`, `NAD_TGEO_GEO`,
the algebra/accessor waves) need no change — they were generated by this rule.

## Note on completeness

The map reflects today's MEOS export surface (`nm -D libmeos.so`, v6 image). Some
symbols a COLLAPSE currently folds into (e.g. tnpoint/tpose spatial-rels) would
become RENAMEs if MEOS later adds the type-specific symbol — re-run the generator
against the new lib and the outcome flips automatically. The map is regenerated,
never hand-edited.
